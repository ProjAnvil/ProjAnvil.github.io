演示停在干净的项目里。生产从混乱的项目开始。

当一个 agent 被要求「修复登录 bug」，它在真实代码库里需要的远不止一个模型和一个工具循环。它需要知道哪个服务负责认证、团队的约定写在哪里、API 契约怎么定义，以及上一轮学到了什么。这些信息大多不在提示词里，而在 agent 周围的基础设施里。

## 三条轴线

我们用一个简单的模型：agent 的上限由三件事决定。

- **执行** — 它能做什么。工具、权限，以及一个可暂停、可检视的运行时。
- **技能** — 它知道什么。经过打包的领域深度，agent 需要时可以直接调用。
- **连接** — 它能触达什么。你的 API、代码与记忆，通过 MCP 暴露出来。

多数团队把精力放在模型上。我们认为更大的杠杆，是用更少但更好的组件把这三条轴线填满。

## 从意图到上线代码

技术栈沿着需求真实流转的路径设计：

1. **Porto** 把 PRD 变成基于现有代码的规格。
2. **SCV** 先把代码库转成机器可读的结构。
3. **Knot** 通过 MCP 暴露 API 契约，agent 可以直接查询。
4. **LadyM** 记住 agent 学到的东西，而不是每轮重新发现。
5. **MindForge** 为每个阶段提供领域专业能力。
6. **WoCA** 驱动整个循环，带权限控制与可检视的图。

每一层只做一件事。这是设计约束，也是各部件能独立使用的原因。

## Go 优先，但不只有 Go

运行时、记忆、图引擎与 SDK 都用 Go 编写。这是有意为之：在 Go 上跑基础设施的团队，不应该为了获得 agent 能力再部署一个 Python 服务。在 Python 更合适的地方——分析、验证、BI——我们就用它，并通过 MCP 或 HTTP 暴露，让它与其余部分协同。

所有仓库都公开、使用 MIT 协议。评估这套东西不需要任何私有权限。
